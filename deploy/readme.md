## Docker Compose

Входные параметры: Docker Engine с Compose, файл `.env` в корне проекта, домен с HTTPS и nginx на сервере.
Выходные параметры: приложение на `127.0.0.1:6553`, фоновый обработчик, каталог `data/` в корне проекта, смонтированный в `/app/data` обоих контейнеров.

Первый запуск:

1. Подготовьте `.env` по [`.env.example`](../.env.example). Используйте независимые случайные секреты длиной от 32 символов. Ключи VAPID можно создать командой `npx web-push generate-vapid-keys`. Задайте настоящий `APP_ORIGIN` (HTTPS без завершающего слеша) и `VAPID_SUBJECT` с рабочим адресом почты. Сохраните `.env` с правами `600`. Не передавайте этот файл в Git или в образ.
2. Создайте `data/backups` в корне проекта: `mkdir -p data/backups`. Укажите в `.env` `APP_UID` и `APP_GID` владельца этого каталога (значения `id -u` и `id -g`; запуск от root не требуется). Выполните `docker compose build`, затем `docker compose up -d --wait`. Сборка использует Node.js 24 и standalone Next.js; для загрузки зависимостей и Google Fonts нужен интернет. Секреты передаются только при запуске.
3. Создайте первого администратора: `docker compose exec -e ADMIN_EMAIL=you@company.ru app node scripts/create-admin.mjs`. Случайный пароль появится в терминале. Автоматических демонстрационных аккаунтов и задач нет. Повторный запуск не меняет существующего главного администратора.
4. Настройте домен и сертификаты в [`deploy/nginx.conf`](nginx.conf), проверьте `nginx -t`, перезагрузите nginx. HTTPS необходим для cookie авторизации, PWA и push.
5. Проверьте `docker compose ps`, `docker compose logs --tail=100 app worker`, вход и создание задачи через HTTPS.

Контейнеры работают от пользователя `node` с UID/GID из `.env`, без дополнительных capabilities. Компилятор и dev-зависимости остаются в стадиях сборки. Приложение проверяет доступность SQLite через `/api/health`; worker запускается после успешной проверки и обращается к приложению по внутренней сети Compose. Проверка готовности не заменяет внешний мониторинг; нездоровый контейнер Docker самостоятельно не перезапускает. Логи ограничены тремя файлами по 10 МБ на сервис.

Используется существующий каталог `./data` рядом с `compose.yaml`; Compose не создаёт его автоматически. Существующая база `data/app.sqlite` доступна контейнерам напрямую. Не запускайте несколько экземпляров приложения или worker для одной базы. Данные, `.env`, исходный `node_modules` и `.git` исключены из контекста сборки. Остановка и удаление контейнеров, включая `docker compose down -v`, сохраняют каталог `data/` на хосте.

Обновление:

```bash
docker compose exec worker node scripts/backup.mjs
docker compose stop worker app
docker compose build
docker compose up -d --wait
```

Перед изменением схемы сохраните копию вне сервера. При изменении `.env` выполните `docker compose up -d --force-recreate --wait`. Не меняйте секрет сессий и VAPID-ключи при обычном обновлении: это сбросит сессии или потребует переподписки на push.

Ручная копия: `docker compose exec worker node scripts/backup.mjs`. Резервные файлы сразу доступны на хосте в `data/backups/`. Настройте регулярное копирование вне сервера средствами инфраструктуры.

Восстановление:

1. Выполните `docker compose stop worker app`.
2. Сохраните весь текущий каталог: `cp -a data data-before-restore`.
3. Скопируйте проверенную копию: `cp ./backup.sqlite ./data/app.sqlite`.
4. Удалите старые WAL и SHM после сохранения исходного каталога: `rm -f ./data/app.sqlite-wal ./data/app.sqlite-shm`. Убедитесь, что каталог и файл базы доступны для записи UID/GID из `.env`.
5. Выполните `docker compose up -d --wait`, проверьте вход, задачи и фотографии. На устройствах удалите старую очередь действий перед работой с восстановленной базой.

## Запуск без Docker через PM2

Развёртывание на сервере: Node.js 22.12+ (рекомендуется 24 LTS), nginx, PM2. Приложение слушает только `127.0.0.1:6553`. SQLite и фотографии хранятся в `data/app.sqlite` в корне проекта.

1. Создайте `data/` в корне проекта и каталог резервных копий, выдайте пользователю приложения права записи, ограничьте доступ остальных пользователей.
2. Выполните `npm ci`. В [`package.json`](../package.json) явно разрешён install-скрипт `better-sqlite3` для сборки нативного модуля. Скопируйте [`.env.example`](../.env.example) в `.env`, задайте независимые случайные `JWT_SECRET` и `MAINTENANCE_SECRET` (не менее 32 символов), `APP_ORIGIN` и пути данных.
3. Выполните `npx web-push generate-vapid-keys`. Сохраните публичный и приватный ключи в соответствующие поля `.env`, задайте реальный `VAPID_SUBJECT=mailto:...`. Приватный ключ не передавайте клиентам.
4. Выполните `npm run build`. Создайте главного администратора командой `node --env-file=.env scripts/create-admin.mjs` с `ADMIN_EMAIL` и `ADMIN_PASSWORD` в окружении.
5. Запустите `pm2 start ecosystem.config.cjs`, затем `pm2 save` и `pm2 startup`; выполните выданную PM2 системную команду для автозапуска. Запускаются приложение и фоновый обработчик.
6. В [`deploy/nginx.conf`](nginx.conf) замените домен и пути сертификата на свои. Подключите конфигурацию nginx, проверьте `nginx -t` и перезагрузите nginx. Откройте HTTPS-адрес, войдите, откройте «Работа», установите PWA и включите уведомления.

`NEXT_PUBLIC_VAPID_PUBLIC_KEY` также возвращается API из окружения процесса. После изменения `.env` перезапустите оба процесса через `pm2 restart ecosystem.config.cjs --update-env`.

Резервное копирование выполняется при старте фонового процесса и раз в сутки; сохраняются последние 30 успешных копий. SQLite Online Backup API даёт согласованный снимок работающей WAL-базы, затем выполняется integrity_check и атомарное переименование. Маркер успеха записывается только после завершения. Повтор после ошибки — на следующем цикле. Ручной запуск: `node --env-file=.env scripts/backup.mjs`.

`BACKUP_DIR` можно направить на отдельно смонтированный диск. Копия на том же диске не защищает от потери сервера: настройте копирование этого каталога во внешнее хранилище средствами инфраструктуры. Проверяйте `pm2 logs sp-planner-worker` и наличие свежего файла; ошибки фоновых задач выводятся в журнал.

Восстановление:
1. Остановите оба PM2-процесса.
2. Сохраните текущий каталог `data/` в корне проекта отдельно, включая `app.sqlite-wal` и `app.sqlite-shm`, если они существуют.
3. Замените `app.sqlite` выбранной проверенной копией, удалите старые `app.sqlite-wal` и `app.sqlite-shm` только после сохранения исходного каталога. Восстановите владельца и права.
4. Запустите PM2, проверьте вход, задачи и фотографии. На устройствах удалите старую очередь действий перед дальнейшей работой с восстановленной базой.

После обновления исходников повторите `npm ci`, `npm run build` и перезапуск PM2. Перед первой миграцией существующей базы сделайте резервную копию. Миграции добавляют таблицы и колонки без удаления задач. Текстовые сроки без года автоматически не преобразуются: уточните их через «Изменить срок».
